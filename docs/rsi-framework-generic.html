A Generic RSI Framework for Agentic Projects

A portable methodology for recursive self-improvement that applies to most agent/LLM projects — plus the contract for a reusable skill that installs the loop into any repo. Grounded in 2026 state-of-the-art. Proposal for review; nothing built yet.

The one invariant (project-independent). Every self-improving system is the same loop: propose a change → score it against a metric → keep it only if it wins → repeat — the Generator–Verifier–Updater (GVU) pattern. The field's hard rule: when the loop stalls or drifts, strengthen the verifier, not the generator. A strong generator + weak verifier reliably optimizes itself into nonsense. Therefore the portable truth is: the fitness signal is the product. Everything else is plumbing.

Four adoption tiers (increasing power & risk)

Generic across projects. A project starts at Tier 0 and climbs only as its verifier earns trust.

TIER 0Grounded self-critique (Reflexion)

Generator produces output → a differently-modeled critic scores it against a concrete rubric → revise. Cap 2 passes. Critic grounded in deterministic checks (not vibes). install-ready no autonomy

TIER 1Automatic prompt/config optimization (DSPy + GEPA)

Treat prompts/configs as compiled artifacts. The optimizer proposes variants, scores each on a holdout set, keeps winners. GEPA's metric_with_feedback returns a reason, not just a number — a "text gradient." production-ready frozen weights

TIER 2Skill / memory accumulation (Voyager)

A growing library of named, reusable routines the project retrieves before solving a task — so improvements compound instead of being re-derived. Base model frozen; only the skill wrapper grows. low risk

TIER 3Self-editing code (SICA / Darwin-Gödel-Machine pattern)

The loop proposes edits to the project's own source, adopted only if they beat the champion on a holdout metric and pass tests, run in a sandbox, with a DGM-style archive + git rollback and a human gate on each adopted change. research-grade pattern sandbox required

Code self-editing is the sharp tier. Copy the design (archive + empirical keep-if-better + diversity-preserving selection), never the published scale — a full Darwin-Gödel-Machine run was ~$22k / ~2 weeks. At single-dev scale: one proposed edit per cycle, tests must pass, git is the rollback, human approves adoption until trust is earned.

Guardrails (project-independent, non-negotiable)

The 2026 literature's cautionary cases are the reason these aren't optional — an optimizer once "improved" a judge by deleting it (the harness defaulted to a passing score); an agent read cached answer keys to fake 100%.

  • Verifier > generator. Spend the eval budget first.
  • Holdout evals. The optimizer never sees the set it's scored on; watch the proxy-vs-holdout gap to catch reward hacking.
  • Canary cases. Plant checks no honest run can pass — a perfect score becomes evidence of cheating.
  • Deterministic wrapper around any judge. Validate schema before scoring, so a malformed/gutted candidate can't silently win.
  • Keep-if-better + archive + rollback. Conservative acceptance; every version scored and reversible (git).
  • Sandbox for the code-editing tier; human gate on high-blast-radius changes; frozen weights to sidestep catastrophic forgetting.

The reusable artifact (the skill contract)

The portable loop ships as an installable Claude Code skill — call it rsi-loop — driven entirely by a per-project config so the same engine runs anywhere:

rsi.config.json # the four plug-ins for THIS project ├─ fitness: { deterministic_checks[], judge_rubric, holdout_glob, canaries[] } ├─ tunables: [ { path, kind: prompt|config|code, sandbox: bool } ] ├─ state: { file, archive_dir } └─ guardrails:{ accept_if: "beats_champion_on_holdout AND tests_pass", human_gate: [ globs that always need approval ], max_changes_per_cycle: 1 } rsi-loop skill # generic engine, project-agnostic observe → diagnose → propose → verify(holdout+canaries) → adopt|rollback → archive

Drop rsi.config.json into any repo, point it at that project's metric and tunables, and the loop applies. ai-efficiency becomes the first config, not a special case.

Worked example — ai-efficiency, the X-fetch inefficiency. Observe: log each of the 12 X sources' latency + yield every run. Diagnose: N accounts are seen-every-run but produce ≈0; the fixed 3s wait and serial fetch dominate latency; the X-search login-wall keeps failing. Propose: demote zero-yield accounts, tune the wait, reorder by hit-rate, reroute the login-wall. Verify: re-run against the last 7 days (holdout) — coverage must hold while latency drops; canary = a day with a known must-catch item. Adopt only if better; else roll back via git. This is one rsi.config.json — the same engine would tune a web app's retry configs or a data pipeline's batch sizes.

Recommended sequencing (any project)

  1. Instrument — log cost + yield + outcome every run. You can't improve what you don't measure.
  2. Build the fitness signal — deterministic checks + judge rubric + holdout + canaries. 80% of the work, 100% of the safety.
  3. Tier 0 grounded critic (free wins).
  4. One narrow Tier-3 loop on the project's biggest measured pain, fully gated — the first real closed loop.
  5. Tiers 1–2 (prompt optimization, skill library) once the verifier is trusted.
  6. Harvest the generic parts into the rsi-loop skill so the next project starts at step 1 with a config, not a rebuild.
