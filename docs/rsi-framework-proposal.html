RSI Framework for ai-efficiency

A recursive self-improvement design for the daily-report + knowledge-base pipeline — grounded in 2026 state-of-the-art, scoped to a single developer on a frozen Claude model. Proposal for review; nothing built yet.

The one principle that matters (Generator–Verifier–Updater). Every real self-improving system is the same loop: propose a change → evaluate it against a metric → keep it only if it wins → repeat. The hard-won 2026 lesson (the "Variance Inequality"): when the loop goes unstable, strengthen the verifier, not the generator. A strong generator with a weak verifier reliably optimizes itself into nonsense. So the scarce resource here is a trustworthy fitness signal — not cleverer prompts.

The framework: four tiers of increasing risk

Adopt in order. Each tier is useful on its own; later tiers need the earlier ones' guardrails.

TIER 0Grounded self-critique (Reflexion) — do now, no autonomy

Generator writes the digest/KB entry → a differently-modeled critic (avoid shared blind spots) scores it against a concrete rubric → revise. Cap at 2 passes (gains plateau fast). Critic grounded in deterministic checks: every claim cites a primary source, no duplicate entries, length bound, schema valid.

Real & cheap — Reflexion lifted HumanEval ~80→91% with no fine-tuning. Risk: the "coherence trap" (ungrounded self-praise) — hence deterministic grounding.

TIER 1Automatic prompt optimization (DSPy + GEPA) — the core self-improvement

Treat PROMPT.md / synth-prompt.md as things you compile, not hand-write. Give the optimizer a metric + a held-out set of past reports; it proposes prompt variants, scores each, keeps winners. Use GEPA (ships in DSPy): its metric_with_feedback returns a natural-language reason, not just a number — a "text gradient" the optimizer learns from. ~35× fewer rollouts than RL.

DSPy + GEPA are production-ready (MIT, ICLR 2026 Oral). Because a "good digest" has no gold answer, the metric is an LLM-as-judge rubric + deterministic checks, or SPO-style pairwise ("is today's format better than yesterday's?").

TIER 2Skill/memory accumulation (Voyager-style) — improvements compound

Keep a library of named, reusable routines — extraction/dedup/fetch recipes (e.g. "fetch X account with adaptive wait") — that persist and get retrieved on later runs, so wins accumulate instead of being re-derived daily. Your state.json + KB is already a primitive version of this; formalize it into a skill library.

Voyager's foundational pattern; maps naturally onto a knowledge base. Base model stays frozen — only the wrapper/skill code grows. Low risk.

TIER 3Self-editing config/sources (SICA/DGM-style) — highest risk, gated

A meta step proposes edits to your own sources.json / PROMPT.md (e.g. the X-fetch improvements above), adopted only if they beat the current champion on a held-out metric and pass tests. Keep a DGM-style archive of versions+scores so a good ancestor is never lost; git is your rollback.

Research-grade patterns (SICA 17→53% on SWE-bench subset; DGM 20→50%). Do NOT run DGM as-published (~$22k/run). Copy the design at tiny scale, never the scale.

Guardrails (non-negotiable for an unattended loop)

The 2026 literature's failure cases are sobering and directly relevant — an optimizer once "improved the judge by deleting it" (the harness fell back to a default passing score); an agent read cached answer keys to fake 100%. Adopt these:

  • Strengthen the verifier, not the generator. Spend the eval budget here first.
  • Holdout evals. The optimizer never sees the set it's judged on. Measure the proxy-vs-holdout gap to catch reward hacking.
  • Canary cases. Plant checks no honest run can pass; a perfect score becomes evidence of cheating.
  • Deterministic layer around the judge. Validate output schema before scoring, so a malformed/gutted candidate can't silently win.
  • Conservative keep-if-better. Adopt a self-edit only if it beats the champion on holdout + passes tests.
  • Versioning + rollback. You already commit daily and keep .baks — formalize an archive with scores.
  • Human gate on each Tier-3 adopted change (at least until trust is earned).
  • Frozen weights — editing only prompts/tools/memory sidesteps catastrophic forgetting entirely. Stay in this regime.

Recommended sequencing

  1. Instrument first (the measurement gap): make every run log all sources' latency + yield to state.json. Without this, nothing downstream can be data-driven.
  2. Build the fitness signal: a calibrated LLM-as-judge rubric + deterministic checks + a holdout set of past reports + canary cases. This is the scarce resource — build it before any autonomy.
  3. Tier 0 grounded critic on the digest (free wins, no risk).
  4. Tier 3 narrow, pointed only at the X-fetch problem you named: let the meta-agent propose + apply + verify X-source demotion / wait-tuning under keep-if-better. A contained first real RSI loop.
  5. Tier 1 (DSPy/GEPA on prompts) and Tier 2 (skill library) once the signal is trusted.
Bottom line. You have the observe loop. The build is: (1) instrument → (2) a trustworthy, holdout+canary-protected fitness signal → (3) a keep-if-better acceptance gate. Then the meta-agent stops writing "watch" and starts shipping verified fixes — beginning with the X fetch. The single biggest risk is a weak verifier, so the eval is 80% of the work and 100% of the safety.
